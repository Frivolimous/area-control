# Mass Battle

Hex-grid, turn-based, multiplayer influence game. TypeScript + webpack + Pixi.js for rendering, Firebase for backend/sync.

## Setup

```
npm install
npm start      # webpack-dev-server
npm run build  # production build to dist/
```

Fill in `src/config/firebaseConfig.ts` with your Firebase project's credentials before running.

## Project structure

```
src/
  index.html          entry HTML (injected by html-webpack-plugin)
  index.ts             entry point — entry screen -> lobby -> active game orchestration
  styles/main.css       layout: entry card, lobby corner panels, config modal, HUD
  config/               firebase project config + game config loader
  types/game.ts          core types (GameState, Player, Tile, GameConfig)
  types/global.d.ts      ambient module declarations (CSS imports)
  firebase/              room lifecycle (create/join/color/name/start/regenerate-map/config) + config fetching
  game/                  pure game logic: hex math, seeded rng, map gen (Voronoi + lakes), influence, turns
  render/                Pixi setup, hex tile rendering, click input, map screen orchestration (incl. regeneration)
  ui/                    entryUI (title/host/join), lobbyUI (player+room panels), configModal, hudUI
  state/                 player identity (localStorage) + pub/sub GameState store
  utils/color.ts          color blending + player palette
  debug/debugHarness.ts  dev-only console harness for map gen / turn engine, no Firebase needed
```

## Tuning notes

**`turnDurationMs`** — no network round-trip limits this (turns are computed locally per client, nothing per-turn touches Firebase), so it's not bounded by latency the way you might expect for multiplayer. What actually limits it:
- **Clock skew between players' devices is the real floor.** Every client computes `currentTurn` from its own `Date.now() - gameStartTimestamp`, with no server correction. Consumer devices can differ by 100-300ms without careful NTP sync. Below ~200-300ms, that skew becomes a full turn or more, and players persistently see different turn numbers (self-corrects over time, not a real desync in final outcome — just visually confusing). Treat ~200-300ms as a practical floor for casual play across assorted phones/laptops.
- **Game-logic compute is cheap at the current map size** — benchmarked at ~6-8ms/turn for 100x100 with up to 20 players (Node, server-grade hardware; expect a few times slower on a phone, still well under any reasonable turn budget). This would NOT hold at the brief's original 1024x1024 default — that benchmarked at ~814ms/turn, nearly consuming a full 1-second turn by itself.
- **Pixi redraw cost hasn't been benchmarked** — happens in-browser, not measurable from this environment. Likely the real bottleneck on lower-end devices, separate from turn-logic speed. `render/mapScreen.ts`'s `tick()` only redraws when a turn actually advanced (not on every poll), which helps, but the redraw itself (thousands of hex `Graphics` objects) is unmeasured.
- Lowering `turnDurationMs` also shortens real-world game length proportionally, since `maxTurns` stays in turn-count terms — e.g. 500 turns at 300ms/turn is ~2.5 minutes vs. ~8.3 minutes at the default 1000ms.

## Open questions / known issues

1. **The whole lobby/entry rework is unverified in-browser.** This was UI/orchestration/Firebase-service work, not game logic — nothing to run through the deterministic-simulation testing used elsewhere in this project. Verification here was type-checking (clean) and careful code review only; I have no way to click through it in this environment. Test the actual flow (entry -> host/join -> name/color/map-select -> new-map/config-edit -> start) before trusting it.

2. **Color palette exhaustion isn't really handled.** `joinRoom` auto-assigns the first unused color from `PLAYER_COLOR_PALETTE` (20 colors); once all 20 are taken, new joiners silently get a possibly-duplicate color via a modulo fallback (`firebase/roomService.ts`). Fine for a happy-hour game sized to the palette, breaks the "unique color" guarantee past 20 players.

3. **Config edit has no shape validation.** The JSON textarea (`ui/configModal.ts`) only checks the input parses as JSON — nothing confirms it actually has `GameConfig`'s fields with the right types. A host pasting a malformed or incomplete config gets it written straight to the room and could produce `NaN`/crashes downstream. Deliberately rough, per how this was asked for ("make it a json in a text area for now").

4. **Regenerate-map / config-edit can race a concurrent tile click.** Both clear every player's `startTile` server-side, but a player mid-click on the *old* map in the instant before their client receives that update could have `selectStartTile` accept a coordinate that isn't valid land on the *new* map — that function only checks "is this tile currently taken," not "is this tile currently active on the current map." Narrow window, not handled (`firebase/roomService.ts`).

5. **Host-only actions are gated client-side only** (New Map, Edit Config, Start Game buttons just aren't shown to non-hosts) — consistent with the rest of the app (no Firestore security rules exist yet for anything), but worth remembering now that more actions carry this same soft gating.

6. **Contested borders can stalemate.** Verified via simulation (not hypothetical): once players' territories meet and neither has open neutral land left to expand into, contested border tiles can reach a stable equilibrium where income and decay cancel out turn after turn, and nobody ever crosses `controlPercentTarget`. `maxTurns` guarantees the game still ends, but doesn't address *why* it stalemates. Worth knowing: since start tiles now begin at max and expansion requires full saturation per ring (see Resolved below), typical games now take ~300–500 turns to resolve, up from ~20–80 before — `maxTurns: 500` is no longer comfortably above the natural range, it's close to where some games land. Worth revisiting once real playtesting (not just simulation) gives a feel for actual pacing.

7. **Overflow/diffusion — alternative to the current "spend on frontier" mechanic.** Instead of capping influence at `maxInfluencePerTile` and spending leftover on random frontier tiles, tiles could accumulate above the cap and "overflow" downhill to neighbors with less influence — closer to a diffusion/erosion simulation, likely producing more organic, wave-like expansion. Not implemented: it's a bigger structural change (redefines what "max" means, needs careful deterministic ordering for cascading overflow across a whole map in one turn) and might independently help or hurt the stalemate issue above. Worth an experiment once the current mechanic has been playtested.

8. **Contested-tile tinting is an extrapolation, not a spec'd rule.** `influenceFillColor` tints a single-influencer tile toward neutral by percent-of-max, as directly requested — but for a *contested* tile (multiple influencers), it blends their colors weighted by relative share and tints the whole thing by total fullness. That multi-player treatment was my own call, not explicitly specified. Flagging in case a different treatment is wanted once it's actually visible in-game.

9. **`BUFFER_MS` (250ms default) is an educated guess, not a measurement.** It exists to give Firestore's realtime listener time to deliver a same-turn focus-change action before a client commits to computing that turn — without it, a fast enough `turnDurationMs` could let a client race ahead of an action still in flight, and since `localTiles` advances incrementally rather than being recomputed from scratch, a missed action means a permanent fork, not a one-frame glitch. I don't have real-world Firestore listener latency data to size this properly; it needs field-testing with actual players on real connections, then tuning down (`render/mapScreen.ts`).

10. **Lakes don't deliberately engineer chokepoints yet.** `game/lakes.ts` places 1-5 lakes at random interior points, each grown as a round, smooth-edged pocket (distance-weighted growth from the seed, same technique as the landmass shaping) rather than a deliberately-narrowed strait between two lakes or a lake and the coast. Reliably connectivity-safe (retries with a fresh seed if a lake would sever the landmass), and larger lakes closer to the landmass's narrower points do create incidental pinches, but nothing is engineered. Worth trying if incidental pinching doesn't feel strategic enough once played with.

11. **Not yet wired up:** spectating, mid-game join, and auth beyond a localStorage-persisted id.

## Resolved

- ~~Map generation looked ugly, hugged every edge, and had no strategic structure~~ — replaced the flood-fill generator with a Voronoi-region-based one: hexes are assigned to their nearest of ~25-50 seeded region points (multi-source BFS, `game/voronoiRegions.ts`), then land is grown region-by-region from the most central region outward (connectivity guaranteed by construction, same reasoning as the old hex-level flood-fill, just with whole Voronoi cells as the atoms being added — this is also what gives the border large-scale coherence instead of single-hex jaggedness). A hard margin (8% of the padded grid's smaller dimension) keeps land off the true grid edge entirely, verified at 0 edge-touching tiles across 30 test seeds. Interior lakes are carved in afterward (`game/lakes.ts`) using the same distance-weighted round-growth technique, each checked to confirm it doesn't sever the landmass into separate islands (retried with a fresh seed if it would, rather than just giving up on that lake).

  Non-obvious finding along the way: naively applying the edge margin within the *same* grid used for `mapLandPercent` created a geometric impossibility at high land percentages — the usable interior after margin clipping was often barely bigger than the land target itself, forcing a nearly-maximal fill that defeated the point. Fixed by generating on a grid 1.4x larger than `mapWidth`/`mapHeight` and computing the land target from the *original* (unpadded) dimensions — the margin comes from genuine extra space instead of competing with the land target. Net effect: `mapWidth`/`mapHeight`/`mapLandPercent` now describe the target land area size rather than a literal grid rectangle; verified this doesn't affect anything downstream since rendering already auto-fits to whatever tiles come back (`render/mapScreen.ts` `fitAndCenter`).

  Region count, lake count, and lake sizing were tuned by averaging results across multiple seeds rather than picked by eye — see the constants and comments in `game/mapGenerator.ts`. First lake pass used many small lakes with uniform-random-frontier growth (inheriting the same jaggedness problem the original land algorithm had); revised to 1-5 larger lakes (up from ~8 small ones) with distance-weighted round growth after feedback that it looked jagged and didn't create interesting chokepoints. Generation time for the real 100x100 config: ~160ms (one-time cost at game start, not per-turn).

  All of the above tuning constants (padding factor, edge margin, region count formula, lake count/size formulas) moved from hardcoded constants to `GameConfig` fields, so they can be adjusted from Firestore without a redeploy — `generateMap` now takes the full `GameConfig` object rather than a narrower bespoke options type. Existing Firestore `config/gameConfig` documents don't need updating: missing fields fall back to the tuned defaults automatically (same merge behavior as every other config field). See the `mapPaddingFactor`/`mapEdgeMargin*`/`mapRegionCount*`/`mapLake*` fields on `GameConfig` in `types/game.ts`.

- ~~Territory expansion capped at 7 tiles forever~~ — the original "spread leftover around the focus" only ever targeted the focus tile's 6 immediate neighbors. Went through several iterations since: spending leftover on the whole territory's frontier; requiring the source tile to be maxed (a paced wavefront); a reinforcement phase so newly-claimed submax tiles could ever reach max; and most recently, superseded entirely by the radius-ring redesign below. Each step found via actual simulation, not code review.
- ~~Start tiles building up from zero~~ — start tiles now begin at max influence when the game actually starts (`render/mapScreen.ts` `startGameLoop`, `debug/debugHarness.ts`), so players can push outward from turn 0 rather than spending the first several turns just filling their own start tile.
- ~~Tile color didn't reflect influence magnitude~~ — `influenceFillColor` now tints toward neutral by percent-of-max rather than snapping to a flat solid color at any nonzero influence. See `utils/color.ts`.
- ~~Cross-client determinism risk from Firestore map field ordering~~ — `Object.values(state.players)` iteration order isn't guaranteed identical across clients (Firestore doesn't publish a field-ordering guarantee for map data), and since players are processed sequentially within a turn, a different order could mean different clients computing different results from the same seed. Fixed by sorting players by id before iterating. See `game/turnEngine.ts`.
- ~~Games that never end~~ — added `GameConfig.maxTurns` (default 500) as a safety net: if nobody hits `controlPercentTarget` by then, the game force-ends and ranks by tiles controlled. Doesn't fix the underlying stalemate mechanism (#1 above), just guarantees termination.
- ~~Tick loop redrew the whole map every poll regardless of whether a turn advanced~~ — `render/mapScreen.ts`'s `tick()` now only calls `renderGameTiles`/`onTick` when the catch-up loop actually advanced at least one turn. Poll interval (`TICK_INTERVAL_MS`) tightened from 100ms to 30ms now that polling more often doesn't cost wasted redraws — this sets a practical floor on `turnDurationMs` responsiveness; see the note on `turnDurationMs` above.
- ~~Focus-tile selection during Active play, and the "host computes turns" authority question it raised~~ — implemented via an append-only `FocusChangedAction` log on `GameState` (rare, player-initiated events, not per-tick data — doesn't reintroduce the write-volume problem) plus `BUFFER_MS` (see Open Questions #9). Click a tile during Active play to toggle it in/out of your focus set; the start tile can't be removed (brief rule 1). Actions apply at `effectiveTurn = submittedTurn + 1`, never immediately, so it doesn't matter whether a client's Firestore listener delivers an action before or after it locally crosses that turn boundary — only that it arrives before the client actually *computes* that turn, which `BUFFER_MS` protects. Every client still computes every turn locally (the "host computes" divergence noted earlier stands), it's just now provably safe to do so with live player input in the mix. "Only your focus is visible to you" (brief) is enforced at render time (`render/mapScreen.ts` `renderGameTiles` only ever highlights the local player's own resolved focus tiles) rather than by withholding data — every client needs everyone's focus data to compute turns correctly regardless.
- ~~Entry/lobby UI was a single combined screen with name/color picked before joining~~ — reworked into a proper flow: a bare title/Host/Join entry screen (`ui/entryUI.ts`), then a lobby screen with two corner panels (`ui/lobbyUI.ts`) — player identity (name, color, host-only New Map/Edit Config) top-left, room info (code, player list, selection hint, host-only Start) top-right — over the same click-to-select map as before. Players now join with a placeholder name and an auto-assigned (transaction-checked unique) color, both changeable in the lobby. Host actions: **New Map** re-rolls the seed; **Edit Config** opens a raw JSON textarea (`ui/configModal.ts`) writing straight to the room's config — both clear every player's start-tile pick, since old coordinates may not be valid on the regenerated map. Map regeneration reuses the existing pixi Application/click-listener (`render/mapRenderer.ts` `reset()`, `render/mapScreen.ts` `regenerateMapScreen`) rather than re-bootstrapping a second canvas. This was UI/service-layer work, not game logic — verified by type-checking and review only, not the simulation-based testing used elsewhere in this project; see Open Questions #1.
- ~~Rule 3 (focus not controlled by player -> line toward it) never actually made progress~~ — found via simulation while testing the newly-wired focus selection: the original approach divided budget evenly across the whole path every turn and always restarted from index 0. Early tiles reached max within a turn or two and then silently absorbed (wasted) every future turn's budget for that focus, since `addInfluence` clamps at max without signaling the spend had no effect — a focus set on a tile 14 hexes away made exactly zero progress after 60 simulated turns. Fixed to walk the path sequentially, fully saturating each tile before advancing to the next.
- ~~Influence spreading redesigned: equal radius-ring distribution, and rule 3 could "cross" gaps in the map~~ — two related fixes, requested together. First: a controlled focus's leftover budget no longer spreads randomly across the player's whole territory frontier — it now expands outward from the *focus itself* in expanding rings (radius 0 = the focus tile, then 1, 2, 3...), splitting budget as evenly as possible within each ring before a wider one gets anything (`game/hexGrid.ts` `hexRing`, `game/influence.ts` `ringExpand`) — verified exact-match arithmetic on a controlled test case (30 budget over 6 radius-1 tiles → exactly 5 each; 100 budget with radius-1 capacity 60 → exactly 40 spilling to radius 2, split 3/4 by remainder). Second: rule 3's line-walk toward an uncontrolled focus previously *skipped* inactive (water/off-grid) tiles rather than stopping at them, which meant influence could cross open water or a map gap in a single turn without ever actually reaching there via contiguous land. Now the walk stops dead at the first gap; verified with a real lake from a generated map (influence maxed 30 tiles up to the water's edge, zero ever appeared on the far side after 300 turns). Any leftover once blocked (or once the whole reachable path is maxed with budget to spare — previously silently wasted, another fix here) now ring-expands from wherever the walk actually got to, exactly as if that tile were a controlled focus — confirmed this isn't just discarded (167 tiles ended up controlled from ring-expansion around the blocked point, vs. ~30 on the direct path alone). Full regression (20 seed/player-count combinations, determinism, performance) re-verified after: turn counts unchanged from before, ~11.7ms/turn (up from ~9.1ms, still trivial), determinism holds.

  Follow-up: rule 3's line-walk always started from the player's literal `startTile`, even once territory had grown far away from it in some other direction — needlessly long, and could hit an unrelated gap near the original start point even when the nearest actual territory had a clean path. Now starts from whichever of the player's controlled tiles is nearest (by hex distance) to the focus (`findNearestControlledTile`), falling back to `startTile` only if the player somehow controls nothing (shouldn't happen in practice, since the start tile is always controlled from turn 0 onward). This is why `controlledTiles` is back in `spreadInfluence`'s signature — needed to search for the nearest one. Verified with a synthetic two-cluster scenario (a "start" and a separate far-away "expanded territory," both controlled): every tile touched by a focus near the expanded cluster landed within distance 5 of it, none scattered along the long path from start — confirmed via before/after diff, not just inspection.
